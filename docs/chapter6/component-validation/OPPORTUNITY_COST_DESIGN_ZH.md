# 探索后开发机会成本实验设计

状态：开发先导设计，尚未授权模型调用。

本文件为阶段 B 完成后的下一轮实验设计。它不改变正在运行的 `phase_b_registered_resume_20261002_r3`，也不把阶段 B 的部分轨迹、历史回放或工程测试当作方法有效性证据。

## 1. 研究问题

当前证据表明，搜索流程本身可以改善初始程序，但尚未证明保护分支或反馈调度在相同预算下有净收益。下一轮首先回答一个更基础且可归因的问题：

> 在完全相同的搜索状态和后续预算下，继续开发当前 validation 最好程序、开发一个质量接近但行为不同的落后候选、以及“先探索再开发一个新方向”，哪一种行动更值得投入？

这里的“值得”同时考虑可靠质量改善、延迟收益、实际请求和 token 成本，以及对当前全局最好程序的机会成本。局部改善或方向数量本身不构成有效性证据。

## 2. 固定行动

每个检查点复制一份共同历史。三类行动使用相同的 planner/coder 接口、输出上限、评价器、后续 proposal 上限和重复规则。

| 标识 | 行动 | 具体执行 |
| --- | --- | --- |
| `I` | incumbent continuation | 从检查点的 validation incumbent 继续开发，最多 4 个 proposal。 |
| `B` | branch continuation | 从预先冻结的、非 incumbent、质量接近且行为不同的候选代表继续开发，最多 4 个 proposal。 |
| `E+` | exploration then development | 先进行一次无父代探索；若产生有效且符合最低质量条件的新方向，随后在同一投资单元内最多开发 3 个 proposal；若探索无效或不合格，按预先规定记录为未成熟单元，不补抽。 |

`E+` 的成本包含探索 proposal、后续开发、失败、截断和评价；不能只比较探索的首个候选，也不能把同一次全局改善同时完整记给 `E+` 和 `B`。

每类行动的重复编号在生成公共检查点前冻结。行动顺序在区块内随机化，但随机种子写入 manifest，不能依据后续结果调整。

## 3. 检查点和样本量

- 使用 8 个独立新区块，每块构造一个早期检查点和一个后期检查点，共 16 个检查点。
- 每个检查点固定执行 `I`、`B`、`E+` 三类行动。
- 每类行动做 2 个模型重复。
- 每次最多 4 个 proposal；`E+` 的第一个 proposal 是探索，其余最多 3 个是同一投资单元的后续开发。
- 延续 proposal 上限为 `16 × 3 × 2 × 4 = 384`；每个 proposal 最多 planner 与 coder 两次请求，因此请求上限为 768，另计公共前缀成本。

检查点先从仅含 probe/validation 的搜索期数据中冻结。选择规则为：

1. incumbent 是公共前缀在 validation 上最好的有效程序；
2. `B` 必须是非 incumbent、有效、validation loss 与 incumbent 的差距在预先冻结范围内、且行为描述不同的候选；
3. 若某个状态没有合格 `B`，该状态保留为 `B_unavailable`，三类行动不补抽新的有利状态；
4. Test 标签、未来轨迹和后续收益不能参与检查点或分支选择。

早期与后期检查点的定义在模型调用前写入 manifest。不得看到延续结果后替换检查点、调整质量容差或增加重复。

## 4. 项目身份和连续性

执行代码必须区分：

- `behavior_cell_id`：探针上的行为簇，可随程序改变；
- `investment_id`：本次有限开发投资单元；
- `lineage_id`：共享累计预算的祖先谱系。

开发后代跨越行为簇时，仍继承原 `investment_id`，不会自动获得新试用额度；行为簇不变也不会自动证明应续期。项目进展以该项目历史最好 validation loss 为参照：

```text
local_gain = max(0, project_best_before - candidate_loss)
global_gain = max(0, incumbent_before - candidate_loss)
```

只有超过预先固定的 epsilon 的严格改善才更新项目最好值和进展计数。退步、重复程序、无效输出和未知成本不能制造新的进展。探索产生的新方向只能在 `E+` 投资单元内获得规定的后续额度。

每个行动都必须记录：父代、投资单元、谱系、行为簇、项目最好值、全局 incumbent、局部改善、全局改善、失败/截断、已知和未知成本、剩余预算及终止原因。

## 5. 主要观测

主要诊断终点按检查点和区块汇总：

1. 相对共同检查点 incumbent 的 validation 最好改善；
2. 相对项目父代的局部改善；
3. 首次超过检查点 incumbent 的 proposal 步数；
4. `E+` 中探索后实际获得后续开发的比例；
5. 延续窗口结束时的成熟收益、单位已知 token 收益和机会成本；
6. validation 改善转化为独立 Test 改善的比例；
7. 完整、无效、截断、provider failure、`sent_unknown` 的数量与成本。

未完成的开发窗口、未知成本和未成熟的延迟收益记为缺失，不能填零。所有请求、proposal 或实例级记录都只是嵌套观测，不是独立实验重复。

Test 只在所有阶段 B 任务终态、公共候选冻结审计通过后一次性开放；Test 结果不回流到续期、行动选择、检查点筛选或协议修改。

## 6. 统计和判定

先在每个区块内合并两个重复和两个检查点，再以 8 个区块作为推断单位。报告区块级配对差值、均值、中位数、区块聚类的置信区间和完整性。若服务中断、缺失状态或未知成本导致某区块无法比较，保留缺失并降低可解释范围，不将其当作零收益。

主要比较为：

```text
benefit_BI  = quality(I) - quality(B)
benefit_EI  = quality(I) - quality(E+)
benefit_EB  = quality(B) - quality(E+)
```

质量使用 Test gap 或 validation loss 的相反方向统一为“正值有利于右侧行动”。TSP 实用收益门槛固定为 0.3 个百分点；这批属于诊断先导，不能因为达到点估计就升级为确认性支持。只有在独立确认批次中，区块级校正区间下限达到预注册门槛，才可支持方法主张。

候选解释规则：

- 若 `B` 或 `E+` 的区间明确低于机会成本门槛，说明相应投资方式可能有净收益；
- 若区间跨越有意义收益和伤害，结论为证据不足；
- 若 `E+` 只提高局部 validation、却在 Test 上不稳定或变差，不把局部进步写成方法收益；
- 若 `E+` 没有可兑现的后续开发，结论仅是探索输出可行性不足，不能外推为“探索无价值”；
- 只有当某种行动在自然搜索中具有足够频率且机会成本比较支持时，才进入阶段 C 的方法候选。

## 7. 阶段 C 的进入规则

阶段 B 只是方向质量和投资期限诊断。不得根据阶段 B 点估计直接宣称 H1/H2/H3 成立。进入自然搜索组件筛查前必须：

1. 所有阶段 B 任务终态并通过候选冻结和归档审计；
2. 明确报告 `I/B/E+` 的完整性、成本和测试转化；
3. 冻结最小候选方法及全部参数；
4. 保留 `SP` 和最强简单固定多分支基线；
5. 只有在阶段 B 显示独立增量后，才加入连续性门控、有限试用或反馈组件；
6. 若某组件没有净增量或有稳定伤害，删除或降级该组件，不通过增加预算、任务或调参维护原始主张。

阶段 C 的自然搜索比较必须使用新的独立区块、共同预算、统一 Test 门槛和预先冻结的主要终点。当前阶段 B 的 partial 轨迹、历史回放和工程测试不能替代该确认实验。

## 8. 运行与归档要求

模型调用固定为本机 OpenCode 的 `minimax-cn-coding-plan / MiniMax-M3`。并发、请求速率、全局暂停、provider 错误分类、未知成本和 `sent_unknown` 规则在启动前冻结。出现连续 provider failure 或额度耗尽时，停止派发未启动任务，保留未启动状态，不自动重试未知请求。

每个阶段至少交付：manifest、源码和依赖 SHA、冻结检查点、逐请求提示/响应/usage、候选程序、事件日志、验证与 Test 表、成本账本、分析脚本、报告、ZIP 和 SHA-256。发布前从 GitHub 回下载并核对所有文件哈希；远端 ref 移动时停止发布并重新核对。

该设计的目的，是先测量“探索后开发”是否值得其机会成本，再决定是否有理由组装更复杂的方向保护或反馈调度。它不预设第六章方案必须有效，最终保留的只能是独立实验支持的最小方法。
