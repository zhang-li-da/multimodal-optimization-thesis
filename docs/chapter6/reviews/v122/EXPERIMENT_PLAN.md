# 从 v1.2.2 到博士章节证据的实验流程

版本 review-v122.1，2026-09-25。**这是待实施方案，不是最终预注册，也没有执行新的模型调用。** 现有 v1.2.2 支持阶段 1 的 F/R 两臂；四臂、选择器、其他任务需独立实现与冻结。

## 1. 先明确要回答的四个问题

| 问题 | 主要比较 | 支持它需要的证据 |
|---|---|---|
| Q1：给竞争分支后续机会是否值得？ | F−N | 独立 test 质量或预先定义的成本效率增量，且解释 B 暴露 |
| Q2：族证据是否超出局部收益？ | R−G；随后 R−P | 族证据实际改变选择，并在独立对照中产生增量 |
| Q3：多个行为模式有何用途？ | 行为集合选择器−同容量质量集合选择器 | 部署测试上的质量/鲁棒性收益，计入选择成本 |
| Q4：结论能否离开当前小任务？ | 冻结最终方法与强基线跨模型/规模/任务 | 新数据上的重复效果或清楚的失效边界 |

现有 16 次 F/R 筛查只回答“完整排序相对 FIFO 是否值得继续研究”，不能同时回答 Q1、Q2、Q3。

## 2. 阶段 0：收尾、冻结，不再无止境增加工程门槛

当前 74 项测试及归档校验已经通过，除非源码变化，不需要反复执行整套历史回放来替代真实实验。

1. 选择并记录一个可用的正式运行环境；CI 的 Windows 3.12.14 下载失败另行修复，不必阻止已验证环境的研究。
2. 复用已保存的新块 3–6 原始坐标与顺序。14 城市 TSP，每块 probe/validation/test = 12/36/60，共 432 个实例；不把这些实例数当作算法独立重复数。
3. 在 `protocol.draft.json` 的副本中明确实际意义阈值、可接受 token 增幅及 provider 版本信息。可把 **0.2 个百分点、25% token 增幅**作为讨论起点，但它们不是数据推导出的标准，也不是已注册值。应结合约 6% 的既有 gap、实际研究目标与预算确定；若只求精度估计，可预先规定区间宽度目标。
4. 最终协议状态改为 `FINAL_PROTOCOL_PENDING_EXECUTION`，与源码一起提交；不要把本审阅文档当成自动批准的最终参数。供应商不提供不可变模型版本时，明确标记未知，并记录请求模型、响应 model ID、时间、端点类型；不能假造固定版本。
5. 确保草案、冻结和实际运行环境一致。仓库中的草案记录 Windows 3.13.5；若换 Linux，当前 `freeze` 会继承草案环境，不能直接假定可执行。应在选定环境重新 `prepare`，核对新草案坐标哈希与原块 3–6 一致，并提交草案；最终冻结前保持工作区干净。源码改变同样需要新准备与验证。
6. 真实接口若需连通性探测，单独标记为工程调用、单独计成本，不使用新区块质量结果、不算矩阵重复。也可让首个计划任务承担首次真实接入；若基础设施失败就按协议保留该失败，不选择性补跑。

## 3. 阶段 1：完成现有 16 次真实搜索

### 3.1 固定实验条件

| 项目 | 配置 |
|---|---|
| 两模型 | 当前草案的 `qwen3.7-plus`、`MiniMax-M3`；首次响应核实实际标识 |
| 两控制器 | F=`niche_fixed_dev`、R=`relational_branch`，均为 V121SearchState |
| 四配对区块 | 3、4、5、6；相同块、模型、种子条件下比较 F/R |
| 每次预算 | 8 个候选时隙；解析/非法候选占时隙；无 token 总上限 |
| 合计 | 16 次搜索，128 个候选时隙；每槽完整 planner/coder 时最多 256 次计划调用 |
| 共同机制 | 相同 niche 普通调度，W 不参与选择，B 容量 3、每条 2 次机会、奇数时隙开发 |
| 唯一区别 | FIFO 耗尽最老条目 vs `q(tag)+0.25*gain/(1+attempts)` |
| 模型参数 | temperature 0.7；planner/coder 输出上限 1800/2000；timeout 120 秒 |
| 运行顺序 | 草案 order seed 9241201；同 provider 按冻结 lane 顺序 |
| 输出选择 | 搜索结束按 `(validation loss, node ID)` 选有效单程序与种子比较器；随后独立 test |

每次搜索程序执行预算、初始规则、提示信息及损失定义保持一致。相同提案数不等于相同 token 或运行时间：这批次只声明同提案预算公平，成本另报。

### 3.2 单次执行与留痕

1. 核验 source/config/data/protocol/environment，确认控制器类和 job ID。
2. 只打开 probe/validation，评价共享初始规则。
3. choose 后保存普通选择、实际选择、候选 B、剩余额度、族统计、分数和暴露信息。
4. 保存 planner/coder 提示及原始响应，记录 provider/request/model/usage。响应先落盘再解析。
5. 执行受限评价；保存程序、行为、逐实例损失、失败原因、父代/全局改进和时间成本。
6. observe 一次，保存准入/淘汰、尝试/成功深度、M、RNG 和 checkpoint；恢复时重放核对。
7. 8 槽结束冻结 best、seed-best、档案 ID/代码；之后才执行 test_stage。
8. 汇总所有计划任务的完成/失败状态，再统一分析。不要看部分 test 后修改剩余任务的预算或阈值。

### 3.3 需要得到哪些结果

每个运行必须有：状态、模型/块/seed、有效提案、模型调用、token 完整性、test gap、validation 选出种子的 test gap、B 尝试、B 有效子代、父代改进、全局改进、成功深度、族分数有差异的时隙、R/G 选择分歧、程序及选择身份。

机制链按“有 B → 多个可选分支 → 有不同族证据 → 实际选择不同 → 后续收益 → 最终 test 收益”报告。分别给出分子、分母和运行间分布，不能把最后一项省略后称“机制有效”。

可沿用先前最低诊断：每模型×控制器汇总至少 4 次 B 评价、1 个有效子代、2 个多条目开发时隙；另报族分数差异和 R/G 分歧。**这些只是可观测性诊断，不是统计功效或性能通过线**。不能按达到这些门槛筛选运行，也不能把“必须有改进”设为纳入条件。

定义主要对比：

$$
\Delta_{m,b}=100(\mathrm{gap}_{R,m,b}-\mathrm{gap}_{F,m,b})\quad\text{（百分点，负值有利于 R）}.
$$

给出全部 16 条结果、每模型 4 个配对差值、均值/中位数/更好更差次数、成本和不完整配对。跨模型汇总先在同块平均，重采样时保留模型配对，以 **4 个区块**为独立单位；不能当作 8 个独立数据集，更不能当作 960 个独立算法重复。小样本区间只作描述，不做“已显著优越”的确认性结论。

### 3.4 负结果如何改变下一步

| 观察 | 决策 |
|---|---|
| 有真实接口/恢复错误 | 分离基础设施与算法失败，保存原批次；修复后另建版本/批次 |
| B 稀少或 R/G 从不分歧 | 该预算下无法识别族排序价值；保留全体质量结果，先做预算/暴露诊断 |
| R 不胜 F，但二者有 B 后续收益 | 不能认定 B 无用；进入 N/F 重点比较，谨慎保留 G/R |
| 暴露充分而 R 无优势或更差 | 停止增加关系图复杂度，优先简单开发策略与失效解释 |
| 两模型方向相反 | 作为模型交互，分别报告；新块复核，不只报平均值 |
| R 有实际收益且成本可接受 | 进入 Q1/Q2 的四臂归因，然后独立确认 |

## 4. 阶段 2：补齐论文核心的四臂归因

### 4.1 需要新实现的对照

| 臂 | 开发池与排序 | 被检验因素 |
|---|---|---|
| N | 无 B，全部时隙走共同 niche 普通调度 | 不保留后续开发机会的基线 |
| F | 同一 B，FIFO | 有限分支开发本身 |
| G | 同一 B，按 `gain/(1+attempts)` | 局部收益排序 |
| R | 同一 B，按完整分数 | 族证据在局部收益之外的增量 |

F/G/R 共同准入、淘汰、额度、开发时隙与 tie-break；N 不使用 B，依然消耗相同候选预算。相同历史的普通时隙应一致；真实历史随后分化是调度效应的一部分，不能强迫复用固定候选序列代替在线生成。反事实排名可诊断选择差异，不能推断未生成子代的收益。

推荐探索规模为 **4 臂×2 模型×4 个全新区块=32 次搜索**。步数依据阶段 1 的暴露情况在执行前统一冻结：若 8 步可辨识就保持；不足时把 16 或 32 步作为新预算设计，所有组一致。8 步时最多 512 次计划 planner/coder 调用，16 步时为 1,024 次；不是自动授权的模型预算。

四臂仍是归因筛查，不是博士结论的样本量保证。若阶段 1 已充分显示 R 无潜力，可缩为 N/F；若未来要主张族证据贡献，就不能删除 R/G 必要对照。

### 4.2 对比与验收

F−N 回答有限开发是否有价值；G−F 回答简单收益排序是否足够；R−G 回答族证据是否有独立增量。预先指定一个主要假设，其他作为探索性；若把多项都作为确认性主张，预先安排多重比较控制，不能事后挑最优对比。

要求得到三类证据：完整运行级 test 差值；对应机制确实有选择机会；同提案预算下的 tokens/时间与失败率。开发子代成功率受各策略选择影响，不能直接视为同一候选的因果比较。

R−G 有希望后才增设 P：仅对“读取族分数”的对应做调用前固定的非恒等置换，不改实际提示标签、准入、历史记录或局部收益项。以 R/P×2 模型×4 新块=16 次作为专项筛查的规划例。若 R 不胜 P，不能声称正确族对应是收益来源。P 不是本版已实现功能。

## 5. 阶段 3：做多模态价值的直接验证

这一阶段可复用已冻结的程序，先不增加 LLM 搜索；新增的是程序执行、描述符评价和选择器训练。

### 5.1 行为辨识：模式数不是充分证据

1. 在看新评价之前，固定程序对选取规则：probe 相似、probe 不同、精确重现三类；小候选集可枚举所有程序对，避免只挑成功案例。
2. 新建与搜索和确认 test 均分离的 `behavior_audit` 实例，保持同一问题分布，另建规模变化集用于外推；不要混淆这两件事。
3. 按冻结的距离/差异阈值，报告原 probe 相近程序在新样本上分开的比例，以及原不同程序在新样本上变得相近的比例、质量差与额外评价成本。
4. 这些是有限样本下的描述符稳定性，不是“真实模式误差率”或语义等价证明。若用于设计 witness，新一轮检验应另留独立样本。

### 5.2 多算法集合：从 oracle 到可部署收益

1. 搜索结束后，仅用搜索 validation/probe 冻结候选集合与最大 K；各集合比较器使用相同 K 上限并报告实际数量。不要按 deployment_test 选择集合。
2. 新建 `router_train/router_dev/deployment_test`；可用每块 120/60/120 个实例、三种生成族均分作可行性起点，执行前按成本与精度需要确定。不是 300 个独立算法重复。
3. 用低成本实例特征、同一简单选择器族与相同训练调参预算比较：validation 最佳单程序；初始三种子集合；同容量 validation top-K 质量集合；质量约束行为档案集合。
4. 超参数只在 router_dev 选择，冻结后一次评价 deployment_test。训练/特征/路由成本单独报告；单程序不应被人为追加选择器开销。
5. 报告平均 gap、逐族 gap、失败率、尾部损失、选择时间、程序运行时间及相对配对增益。若使用回退规则，应仅用开发数据定阈值。
6. test oracle 可画成潜力上界，但不能当成选择器成绩。选择器执行了所有程序再挑最好时，其全量执行成本必须计入，不能称廉价路由。

若行为集合只胜单程序而不胜 top-K 质量集合，最多说明多候选有用，不能归因于行为多样性；若只胜初始规则集，最多说明新程序集合更好。无收益时，允许将多模态档案定位为搜索辅助；但相应论文主张必须收缩，不能把“模式多了”直接等同于成果更好。

## 6. 阶段 4：独立确认、强基线与泛化

1. 根据筛查结果选定最终方法、一个主要指标、最强内部基线；再选一个最接近且可公平运行的外部方法。报告作者实现或适配实现的区别。
2. 冻结后用全新任务区块确认。每区块保持两模型配对；增加搜索 seed 时视为区块内嵌套重复。先由 pilot 的区块级差异、预先确定的实际收益阈值 δ 和目标精度做样本量/功效规划。
3. 两臂×两模型×10 块=40 次仅是预算示例；若加入一个外部基线成为三臂，则同样十块为60 次。不能把“做满 40 次”当作天然统计充分，更不能用旧混杂效应估计新版所需样本量。
4. 效果判定区分方向与实际意义：定义 Δ 为方法减基线，低为好；95% 区间整体低于 0 支持方向，整体低于 −δ 才更强地支持达到预定实际收益。区间跨越有利/无利区间时应说证据不确定；未显著不是等价。若追求同质量低成本，须事先定义非劣界与成本指标。
5. 成本公平：现有 runner 是同提案预算。先报告质量随提案和已用 tokens/时间的轨迹；最终若主张同 token 优势，应实现、测试并冻结 token cap 和越界请求计费规则，各组一致，不能事后只选有利预算点。记录搜索、程序评估与部署成本。
6. 预算敏感性可在统一 8/16/32 步长运行中，预先固定相应 readout；只要策略不依赖不同总时限，前缀可作配对重复测量。不能把同一长运行三个前缀当成三个独立搜索，不能看 test 后决定哪一个是主预算。
7. 泛化先做新实例与 TSP 规模外推，再决定是否重新在大规模任务搜索。更大城市数若用近似参考解，报告相对参考解 gap；没有精确最优就不称最优 gap。
8. 若最终声称“通用算法发现 agent”，需至少一个性质不同的第二任务并在该任务独立搜索验证；仅把 TSP 生成程序跑在更大城市数不能支撑跨任务。装箱需先在开发集检验强规则是否形成天花板；不要为了胜出削弱最佳适应等强基线。当前 v1.2.2 runner 仅支持 TSP，第二任务需新接入。

## 7. 失败处理和数据纪律

候选解析/执行失败占用槽位，不能额外生成补位；API 不确定请求保留状态并停止，不自动重发；usage 缺失保留 null 与已知部分，不填 0；缺失配对数量和原因全部报告。若能恢复中断时最佳程序，可报部分预算 anytime 结果，不能伪装成完整八步成绩。不要只保留有 B、有收益或顺利完成的运行。

探索批次可指导下一版；一旦 test 被用于机制或参数决策，就不能再作为该版本的独立确认数据。程序对、集合容量、路由器、阈值和主对比都要在对应 test 之前固定。运行失败或方法变更时新建批次，不覆盖原档案。

## 8. 交付表与版本顺序

| 优先级 | 下一项交付 | 完成标准 |
|---|---|---|
| P0 | 最终协议 + 16 项真实运行状态表 | 每项都有完整结果或明确失败状态；无选择性替换 |
| P0 | F/R 质量、成本、暴露报告 | 全体数据；正确区块配对；明确是否有族选择机会 |
| P1 | N/F/G/R 新版本与归因批次 | 各差异有清楚定义；不能用旧 r2 混入新重复 |
| P1 | 一个明确的多模态价值实验 | 行为辨识可靠性或集合用途，与章节主张匹配 |
| P1 | 最终方法的独立确认 | 最强简单对照与近邻基线，区间和实际意义均报告 |
| P2 | 规模/第二任务与可选 P/W/witness | 由研究主张和已有证据决定，不把所有组件同时开启 |

版本顺序建议：工程冻结提交 → 最终协议提交 → 冻结 manifest 与数据 → 原始运行与不可变结果 → 分析脚本与报告 → 独立审阅。源码、协议、数据和结果可用不同提交/标签定位；不移动旧标签来表示“修正版”。本报告属于审阅文档，不应打成新方法已完成或新实验成功的发布标签。
