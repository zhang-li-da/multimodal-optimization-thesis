# 开题演示建议与逐幕脚本

版本 review-v122.1，2026-09-25。**建议补两个短 demo，总时长约 4–5 分钟。当前报告只提供脚本和已有证据入口，不声称已制作新的演示界面或录屏。** 工程基础足以先做开题演示，不必等确认性优势成立。

## 1. Demo A：真实模型如何发现并继续开发一个程序

目的：让评审看到搜索对象是可执行规则，agent 的生成、执行、反馈和开发形成闭环。

数据源优先使用已有真实 `screening-20260924-r2` 原始归档；新 16 次真实搜索完成后可增加独立页面。所有画面固定显示批次、源码版本、模型、block、运行 ID，以及“历史真实模型运行回放”。不能把旧控制器过程标成 v1.2.2 的新真实实验。

| 时间 | 画面 | 讲解要点 |
|---|---|---|
| 0:00–0:25 | 问题实例族、初始规则、8 槽预算 | 外层搜索跨实例规则，不是让模型直接给一条 TSP 路线 |
| 0:25–0:55 | 某一候选的 plan、代码 diff、实际评价 | 文字策略与实际执行分别记录；合法不代表更好 |
| 0:55–1:35 | 谱系树、B 剩余额度、父代与子代质量 | 解释为什么一个相对父代进步且有竞争力的分支值得获得有限机会 |
| 1:35–2:05 | validation 轨迹与冻结输出 | 父代改进、全局改进分开显示；测试只展示被冻结程序的结果 |
| 2:05–2:30 | 全批次结果概览 | 展示成功与失败，旧关系排序没有优于固定开发，转入当前研究问题 |

案例选取规则：先冻结“第一个满足竞争性局部改进并发生后续开发的运行/节点”或明确写出选择理由，再展示该节点；提供全部运行下拉列表或附录索引。单个案例是说明，不是平均效果证据。若某条轨迹没有再改进，如实显示预算消耗和分支终止。

建议图件：同一运行的程序谱系、质量随提案变化、A/B 状态、一次父子程序在同一实例上的路线差异。路线图只是实例说明，不能凭一张图判两个程序属于不同真实算法模式。

不必现场调用模型。使用固定归档录屏或离线回放可提高可演示性；画面明确写“回放”，不要伪装成现场生成。

## 2. Demo B：为什么关系证据可能改变预算分配

目的：说明方法的可检验机制，并自然引出“改变选择是否真的有用”的后续实验。

来源：`experiments/chapter6/v12_1/test_mechanism.py::two_branches` 与 `experiments/chapter6/v12_2/test_runner.py::test_decision_exposure_distinguishes_multi_branch_from_family_information`。它们使用人工构造评价，必须始终显示 **“控制用例 / 合成反馈 / 零模型调用”**。

固定相同父代增益和使用次数，只改变已观察族证据；不要在界面里把改善后的未来结果编出来。

| 场景 | 应展示的真实控制器输出 | 可以得出的结论 |
|---|---|---|
| 两分支等 gain，local_distance 有两次额外失败 | FIFO 选 2；完整排序选 3 | 在同历史条件下，族信息可以改变下一父代 |
| 将两次失败对应到 return_aware | 完整排序改选 2 | 决策随证据对应变化，而非固定偏好某个 ID |
| 将两次失败对应到第三族 hybrid | 两候选族都回退，R/G 不分歧 | 没有可区分证据时，不应声称关系机制生效 |
| 一个被选子代无效 | 该分支机会扣减；成功深度不增加 | 有限预算规则能处理失败，不无限续命 |

建议左侧显示两个父代的 gain、attempts、remaining；右侧显示各族样本数、回退标记、q、总分；中间显示 F/G/R 各自选谁。机制演示约 90 秒，最后用一句话结束：“这证明规则会改变选择；是否提升独立测试质量，将由真实配对实验检验。”

**现有两个完整 fixture 的族分数差异和 R/G 分歧都是 0，不能直接用它们声称‘关系引导优于 FIFO’。** 它们适合演示恢复、非法输出、冻结与测试隔离，不适合演示族排序增量。

## 3. Demo C：多个算法如何服务不同实例（条件满足后再做）

只有完成独立选择器实验后才展示。输入一个未参与搜索或选择器训练的新实例，由冻结的实例特征选择器选一个程序；同时显示选择耗时、程序耗时、实际 gap 和单程序基线。展示不同实例族的聚合效果及失败回退。

若当前只能逐个执行全部程序后选最优，必须标“oracle 上界 / 执行全部候选”，并显示总执行成本；不能包装成部署时无需知道答案的智能选择。

该 demo 比聊天窗口更直接体现多模态算法集合的用途，但不是当前开题展示的必要前置条件。

## 4. 开题报告中的配套四页

1. **问题页：** 有潜力的局部改进可能因有限行为观察或单一最优保留而失去后续机会；用真实历史例子说明研究动机。
2. **方法页：** 程序生成/评价、A 代表档案、B 有限开发池、M 反馈、独立测试；W 标为未启用的可选研究因素。
3. **已有基础页：** 18 次历史真实搜索；新运行器 74 项测试通过；新版本真实搜索尚未开展。把历史结果与工程验证分两栏。
4. **验证计划页：** 16 次 F/R 筛查 → N/F/G/R 归因 → 多模态价值与独立确认；列出负结果如何调整研究方向。

建议口头表述：“我们已经完成可追溯的自动程序搜索原型，并通过前期实验发现简单多样性维护和关系调度不必然改善质量。第六章拟研究有限预算下的质量保护分支开发，并通过逐因素对照检验关系信息和多算法集合的增量。”

避免把 74 项工程测试称为 74 次效果实验、把 330 项历史程序回放称为 330 次新搜索、把合成用例称为真实模型收益，或把 program tag 当成已验证的程序语义。

## 5. 演示交付验收

建议交付一个离线回放页面或 notebook、一段约 4–5 分钟录屏及静态截图备用。页面读取已冻结归档，附 evidence 路径/哈希；每张截图保留真实/合成/历史版本标签。只要这两项能清楚解释研究对象、机制和未解决问题，开题展示已足够；无需为了形式增加多 agent 聊天界面或复杂平台。
