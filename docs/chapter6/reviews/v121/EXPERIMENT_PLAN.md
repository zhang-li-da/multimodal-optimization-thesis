# 第六章后续实验流程：从离线正确性到搜索与集合价值

版本：审阅方案 v1.0，2026-09-24。依据 `e5d79fd18cae3ec7175a4ca5151dd4924386e060`。**本文件是建议方案，不是已执行实验，不自动替代现有协议，不构成已完成预注册。** 每个在线阶段开始前，需把最终选择写入新协议、源码提交和 manifest。

## 1. 分开回答三个研究问题

| 问题 | 主要对照 | 能支持的结论 |
|---|---|---|
| H1：组合分支排序是否值得使用？ | FIFO vs 族证据+局部收益；其余机制相同 | 组合策略在固定提案预算下的效果 |
| H2：族证据是否有增量？ | gain-only vs 族证据+收益；再加打乱证据控制 | 族证据是否提供超出局部收益的信息 |
| H3：保留多个程序是否有用途？ | 发现集合选择器 vs 种子集选择器/最佳单程序/同容量集合 | 新实例上的可部署组合价值 |

H1 阳性不能替代 H2；oracle gap 小不能替代 H3。离线换父代后的旧候选评价不能当作任何一个假设的在线样本。

## 2. 阶段 A：启动准备与验收，新增模型调用 0

### A1. 固定软件与归档读取

1. 从明确的审阅基线创建新开发分支；保留 v1.2 与 v1.2.1 历史标签。
2. 为 ZIP 建立统一成员名称索引，拒绝规范化后重名；直接校验读取字节，不重打包旧 ZIP。
3. 校验清单只包含实际发布文件，排除 `__pycache__`、临时文件与自身。
4. 锁定 Python、依赖、操作系统/容器信息。旧 r2 验证可使用 Python 3.13.5；新结构哈希要明确定义格式版本，同时保存原始代码 SHA-256。旧 AST 哈希只做有来源的兼容核查。
5. 跨平台记录区分字段严格一致、数值容差一致、结构哈希格式兼容，绝不把三者合并成未说明的“全部通过”。

现有可执行检查命令见 [REVIEW.md](REVIEW.md)。本审阅的 ZIP 适配和哈希诊断是辅助脚本，正式维护版仍需修复公开入口。

### A2. 新建在线入口，禁止误跑旧控制器

建立独立的 v1.2.1 在线入口/版本目录，不调用旧 `v12/run_v12.py` 执行新研究。入口至少需要：

| 能力 | 验收条件 |
|---|---|
| 控制器构造 | 配置显式写入 `chapter6_demo.v12_1_controller.V121SearchState`；启动时实例类型与协议一致 |
| 无调用 dry-run | 输出 16 项配置与指纹，封禁网络与模型客户端，调用计数 0 |
| 假模型全链路 | 覆盖 planner、coder、解析、合法/非法程序、评价、B 消费、报告和 checkpoint |
| 真正有限额度 | 同一提案只扣一次；失败/重复也扣；中断恢复不能刷新额度或重复请求 |
| 完整状态恢复 | 逐 live 节点 choose→核对选择和 allocation→observe；恢复的池、成功谱系、决策历史、RNG、下一提示与连续执行一致 |
| 提案一致性 | 保存选择时不可变副本；候选的父代、标签、操作、参考及 allocation 必须对应该选择 |
| 测试隔离 | 搜索进程不读取 test 评价；搜索结束先保存 validation 选优 ID 和输出集合，再进入独立测试阶段 |
| 历史结果隔离 | 新输出目录，新配置字段；配置或源码不一致时拒绝复用旧结果 |

旧 runner 会自动拟合一个 selector，阶段 B 不应沿用该输出作为集合有效性证据；集合研究在阶段 D 单独实施。

### A3. 控制器验收

保留并执行已有 31 项测试。补充有明确风险针对性的集成检查：

- 两个策略从完全相同状态和 RNG 出发，非开发步骤的完整选择/提示相同；现实两条搜索轨迹因生成结果不同而分化后，不能要求它们的提示继续相同。
- 在两个以上条目、相同局部收益/使用次数的状态下，改变族证据能改变实际选择；同时有族分数相同的负对照。
- 已过期条目不能选中；溢出、失败、重复均按冻结规则处理；成功深度不依赖条目是否仍在 B。
- 在普通步骤后、开发步骤后、planner 返回后/coder 请求前、请求未确定返回时构造中断。确定返回的结果不重复调用；状态不明时停止并记为基础设施事件。
- 改动 test 内容不会改变搜索期间选择、validation 选优 ID 或输出集合；独立 evaluator 才能访问 test。

### A4. 新数据与源代码冻结

新区块使用 3、4、5、6。当前预检查得到 432 个实例（每块 12 probe + 36 validation + 60 test），ID/精确坐标未与旧 324 个实例重复。正式步骤：

1. 一次性生成并保存所有坐标；记录 ID、family、生成版本、完整文件哈希与 split 哈希；之后只读快照。
2. 同一区块、两个模型和两个控制器共享数据划分与初始规则；搜索随机种子显式记为 block ID。
3. 启动前检查新旧实例 ID、内容、split 间重叠；不能因为测试难度不理想重新挑选这些已见过 test 的区块。
4. 先提交可运行源码与最终协议，得到不可变 source SHA；再写 manifest 并记录源文件指纹、数据哈希、环境和顺序。manifest/结果文件不反向进入其引用的源码指纹，避免循环依赖。
5. 模型记录 provider、发送的 model ID、返回的 model ID/版本与时间窗口。服务不提供不可变版本时如实标记未知，不能只靠别名宣称完全可复现。

**阶段 A 出口：** 控制器与 runner 集成、恢复、测试隔离通过；所有发布材料可读；哈希格式差异有明确处理方案。未满足则不发模型请求。

## 3. 阶段 B：16 次新搜索，检验 H1

### B1. 固定实验矩阵

| 项目 | 建议冻结值 |
|---|---|
| 模型 | 现有 Qwen / MiniMax 两个端点；使用冻结时记录的实际标识 |
| 控制器 | `niche_fixed_dev`、`relational_branch`，均由 V121SearchState 实例化 |
| 区块 | 3、4、5、6；所有配对使用相同区块 |
| 任务 | 14 城市 TSP；每次构造后固定 24 次 2-opt 检查 |
| 种子 | 相同三条手写规则 |
| 数据 | probe/validation/test = 12/36/60，三种现有实例族 |
| 搜索预算 | 每运行 8 个总提案；无 token 上限；无效候选占用时隙 |
| 模型参数 | 建议沿用当前显式参数：temperature 0.7，planner 输出上限 1800，coder 2000；接入时核实并写入 manifest |
| 普通调度 | 相同 niche 规则、父代/操作/参考逻辑与 RNG 消耗 |
| B | 容量 3，每条 2 次；奇数时隙且池非空时开发；两组共同 refine、不带参考 |
| 竞争性 | 沿用当前准入时质量带 0.035、父代增益阈值 1e-4；不事后调参 |
| W | 禁止参与选择 |
| 唯一策略差异 | FIFO 耗尽最老条目 vs `q(tag)+0.25*gain/(1+attempts)` |
| 运行顺序 | seed 9241201 生成后冻结；已提供同顺序的任务矩阵草案 |

总量为 16 次搜索、128 个候选时隙；所有 planner/coder 请求都成功时为 256 次调用。按旧 r2 的平均用量粗估约 **35 万 tokens**，这只是历史预算参考，不是上限或新端点报价。无 token 上限的实验只支持“相同提案数”比较，不能宣称严格相同 tokens 成本。

`screening_16_jobs.draft.json` 是任务清单，不是 runner，也不是预注册 manifest；不要交给旧启动器运行。若采用每 provider 一条执行 lane，应在 manifest 保存每 lane 的冻结顺序，同时记录真实开始/结束时间，不能把并发执行写成严格全局顺序。

### B2. 单次搜索流程

1. 校验 source SHA/指纹、controller class、数据哈希和配置；初始化三条共享规则，只计算 probe/validation。
2. 在每个 step 调用一次 choose；持久化父代、目标族、参考、操作、可用集合、每条额度、族统计、局部收益与总分。
3. 记录最终提示及提示哈希，再请求 planner；保留原始响应、request ID、usage、时长。
4. 请求 coder 并记录同类材料；解析失败或非法程序转成失败候选，保留原因并消费当前时隙。
5. 执行受限程序，保存逐实例损失、行为、轨迹、合法性、特征/局部检查次数和 CPU 时间。
6. observe 一次并记下资格、实际入池、淘汰、额度变化、尝试深度、成功深度；原子保存 checkpoint，清理已确定完成的 pending 状态。
7. 8 个时隙结束后，按 `(validation loss, node ID)` 确定最佳有效程序；种子比较器也仅按 validation 选。固定输出 ID/代码哈希并存档。
8. 独立测试阶段加载冻结程序，在 test 上一次性计算主要质量指标；测试结果不返回搜索或用于挑选另一个程序。
9. 对完整运行重放决策、评价和预算；检验新控制器配置不是旧 V12SearchState。

### B3. 失败与缺失规则

- **候选失败：** 编译/解析/运行失败属于算法运行结果，消耗时隙；已有种子可提供最终有效输出。不能用新候选补位。
- **API/基础设施失败：** 无响应可能已计费，保存 pending/request ID，不静默重试。失去确定完成状态时停止该运行并标记原因。
- **usage 缺失：** 保留已观察质量结果，但成本不完整，不能填 0 或宣称成本公平。
- **整次运行中断：** 在 16 项流转表中保留该项。若能重建当时最佳程序，可额外报告“截至中断的 anytime 结果”，不能伪装成 8 时隙完成结果。
- **不完整配对：** 报告缺失数量及分组原因；完成配对分析标为描述性且说明可能有选择偏差；不能为了凑齐 16 项挑选重跑成功结果。
- **低 B 暴露/零改进：** 属于可解释的负结果，仍纳入全体运行质量汇总；不按机制成功筛样本。

上述规则应在调用前写入最终协议。若服务故障导致设计不可解释，保留失败批次，另建新批次，而不是覆盖。

### B4. 必需输出字段

| 粒度 | 字段与用途 |
|---|---|
| run | source/data/config 哈希，model/provider，block/seed，状态，实际提案和调用数，usage 完整性，token/CPU/墙钟成本 |
| decision | 普通决策、最终决策、B 可选 ID、remaining/attempts、族样本数和分数、局部项、chosen ID |
| exposure | 是否 B 时隙、是否至少两条、不同 tag 数、是否族分数有差异、full 与 gain-only 是否选择不同 |
| candidate | 父代/参考/操作/allocated_tag、原始代码和结构哈希、评价、重复类别、父代/全局改进 |
| branch | 资格、实际保留、淘汰、扣款、attempt/success depth、选择时相对当前最佳质量差 |
| readout | validation 选优 ID、seed 选优 ID、集合 ID、冻结时间、test gap、所有选择仅使用哪一划分 |

`allocated_tag` 是控制器请求的修改族，不保证程序确实实现该机制；`reported_tags` 与执行行为应单独记录，不将标签本身当成语义真值。

### B5. 机制暴露与质量分析

沿用当前草案的最低诊断：每个模型×控制器单元至少 4 次 B 后续评价、1 个有效子代、2 个多条目时隙。再报告族分数不同和 full-vs-gain 决策分歧次数；它们用于判断族信号是否真正有选择机会。

不把改进次数作为纳入条件。不要只比较触发 B 的运行，也不要将两个控制器各自挑出的子代成功率直接解释为因果效果。

主要质量为 validation 选出的单程序 test 平均 gap。定义每个配对：

\[
\Delta_{m,b}=\mathrm{gap}_{\mathrm{full},m,b}-\mathrm{gap}_{\mathrm{FIFO},m,b}.
\]

负值有利于完整排序。报告 16 个运行、每模型 4 个差值、各模型均值/中位数及更好/更差次数。两个模型共享同一数据区块，跨模型汇总时先计算区块平均差，再以 **4 个区块**为重采样单位，保持模型配对；不能当作 8 个互不相关的数据集。

四区块区间分辨率很低，bootstrap/其他区间只作描述。预先指定 H1 唯一主要对比；其他质量、深度和模式数量为次要诊断。展示质量随提案与 tokens 的曲线，但不靠事后选择预算点制造优势。

### B6. 完成后如何决定下一步

| 观察 | 后续行动 |
|---|---|
| 实现/恢复/数据检查失败 | 修复并标注批次有效性；不讨论性能机制结论 |
| 几乎没有 B 或族证据选择机会 | 判断当前 8 时隙设计不足以检验排序；仍报告全部质量结果；若需更长预算，另建冻结协议 |
| 暴露充分，两个模型均无实际改善迹象 | 暂停该族排序，保留 FIFO 与失败边界研究；不立即加复杂图 |
| 两个模型方向相反 | 报告模型交互与逐区块差异，不把平均值作为通用结论；用新块复核 |
| 效果有希望且成本可接受 | 进入 H2 的独立机制归因批次 |

“有希望”用于研发决策，不是显著性判定。建议调用前把最小实际收益阈值具体化，例如 **0.2 个百分点**仅为待作者接受的规划示例，不是从现有数据推导出的真值或已注册门槛；同时设定可接受 token 增量范围。

## 4. 阶段 C：隔离族信息的增量，独立新批次

若阶段 B 值得继续，建议一次四臂机制筛查，所有共同机制和新数据再次冻结：

| 臂 | B 内排序 | 作用 |
|---|---|---|
| F | FIFO | 固定简单基线 |
| G | `gain/(1+attempts)` | 排除局部收益项本身的贡献 |
| R | `q(tag)+0.25*gain/(1+attempts)` | 完整组合 |
| P | `q(permuted_tag)+0.25*gain/(1+attempts)` | 检查证据与正确标签的对应是否重要 |

建议初始规模为 **4 臂×2 模型×4 全新区块=32 次**，作为独立归因筛查，仍不宣称确认性。若预算不足，可先采用 G/R 两臂×两模型×四新块=16 次；代价是暂不能通过打乱证据控制说明标签对应的作用。

打乱映射仅用于读取族分数，不改变真实提示标签、B 准入或历史记录；每个运行使用调用前冻结的、独立于结果的非恒等排列并保存 seed。不要逐次试多个排列直到得到理想差异。R−G 是 H2 的主要对比，R−P 为证据对齐诊断，R−F 为连接性次要对比。

这些方案须在阶段 B 后择一并冻结，不能同时查看多个设计的测试结果再挑选。新块不能复用已用于调参或观察策略优劣的 0–6 区块。

## 5. 阶段 D：多算法集合是否真正可用

本阶段先不增加 LLM 搜索预算，复用已冻结的候选代码，在新实例上做程序执行与选择器训练。若后续改变搜索过程，另记为新实验。

1. 对每次搜索先冻结集合构建规则和最大容量 K，使用搜索 validation 的质量/行为证据选集合，不能看 test；共同设定 K 上限，报告实际有效容量。
2. 新建互不重叠的 `router_train`、`router_dev`、`deployment_test`。建议最小部署可行性规模为每搜索区块 120/60/120 个实例，三族均分，成本可估算后再冻结；它们不是额外的算法独立重复。
3. 同样训练/调参预算下比较：validation 最佳单程序；初始三规则集选择器；按 validation 质量选取的同容量候选集合选择器；质量/行为档案集合选择器。
4. 首先使用简单、低成本的实例特征选择器。超参数只在 router_dev 决定，置信不足回退到 validation 最佳规则。不得用 `deployment_test` 选择算法或调参。
5. 给出新实例 gap、失败率、选择时间、特征成本、程序执行时间，以及相对最佳单规则的配对增益。oracle 仍单独作上界，不是可部署成绩。
6. 若发现集合优于种子集但不优于同容量高质量集合，收益可能来自更好的候选而非行为多样性；若只优于单规则，则不能直接归因于多模态档案机制。

程序模型选择使用的数据不能重新喂给搜索。如果目标还包括部署分布外泛化，另划全新 family/参数范围作为外推测试，不与开发集混用。

## 6. 阶段 E：确认、扩展与论文贡献

- 只对筛查后保留的一个主假设和最终方法做确认；新测试块在方案冻结前不用于开发。
- 通过阶段 B/C 的配对方差和事先约定的实际收益阈值进行功效/精度规划。独立单位是数据区块或预定义任务区块；同块多模型或多搜索 seed 为嵌套重复。旧 r2 的混杂效应不能直接当作新方法预期效应。
- “40 次”若采用两臂×两模型×十块，只是一个预算候选，不能自动代表样本量充分。不同任务、块数与预算下需重新评估。
- 扩展到更大 TSP 规模和至少一个第二任务。更大规模时预先说明参考解来源和 gap 分母；没有精确最优不能写成精确最优 gap。
- 若用现有 binpack，先离线检查强手写规则是否已使所有候选几乎无差异；避免为了得到优势而临时削弱规则基线。任务校准只用开发数据。
- 只有核心质量或集合用途有可重复增量后，再单独检验 W、witness、复杂关系图；每项都需同信息、同预算的简单对照。

## 7. 输出包与版本管理

每一批次至少包含：最终协议、冻结 source SHA/tree 和依赖信息、完整实例文件、manifest、逐运行状态、提示/响应/usage、候选代码、逐步事件、checkpoint、冻结输出 ID、验证报告、运行级/配对级表及生成报告脚本。

推荐过程：开发分支→通过阶段 A→源码冻结提交/标签→创建 manifest→运行→生成结果提交/标签→独立复核。冻结后的错误通过补充勘误与新标签表达；旧结果不改写、不混入新重复，方法变更后使用新实验 ID。

本次交付只发布审阅、诊断证据和实验设计；没有运行新模型搜索，也没有将未完成的在线入口标为可执行。
