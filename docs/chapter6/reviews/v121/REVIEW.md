# v1.2.1 独立审阅：实现已修正，下一步验证搜索价值

审阅日期：2026-09-24；审阅版本：[`e5d79fd18cae3ec7175a4ca5151dd4924386e060`](https://github.com/zhang-li-da/multimodal-optimization-thesis/commit/e5d79fd18cae3ec7175a4ca5151dd4924386e060)。本文为事后独立审阅。新增模型调用 **0**，新增在线搜索 **0**。审阅文件与原始实验分开保存，不更改旧控制器、旧标签或原始 ZIP。

## 1. 总体判断

v1.2.1 已落实上一轮最重要的修正：统一普通调度、明确关闭 W、严格 FIFO、拆分尝试与成功深度，并加入真正能区分分支选择的测试。应当将研究阶段从“修复对照混杂”推进到“补齐在线闭环并检验策略价值”。

但当前仍只有旧 r2 的真实模型搜索结果；新控制器只有离线证据。**不能把旧性能数字移作 v1.2.1 的性能，也不能把离线改变父代的次数当成收益。** 推荐补齐第 4 节启动条件，然后按[详细实验流程](EXPERIMENT_PLAN.md)执行 16 次筛查，不立即扩至 40 次。

## 2. 已完成且本次验证的改进

| 上轮问题 | v1.2.1 实现与证据 | 本次判断 |
|---|---|---|
| 普通步骤使用不同控制器 | 两组都调用 `SearchState.choose` 的 niche 分支；族统计独立计算；普通选择使用相同随机数路径 | 原主要混杂已在实现层消除 |
| W 暗中参与参考选择 | `observe()` 清空 W；普通选择只用 A；测试额外注入 W 诱饵 | 修正成立 |
| 固定基线被错误命名为 FIFO | 选择可用集合最老条目，耗尽后继续 | 实现与新定义一致 |
| 失败续接也增长成功深度 | 独立维护 `success_depths`、尝试深度和成功深度；祖先淘汰后仍保留谱系 | 修正成立 |
| 只有一个分支的“选择测试” | 两条等收益分支、不同族历史，实际 `choose()` 按预期改变父代 | 族信号确实进入决策 |
| 入池资格与实际保留混用 | 区分 `branch_eligible`、`branch_admitted`、淘汰对象 | 审计粒度改善 |
| 同历史回放遗漏额度消耗 | 两个副本沿各自 allocation 推进并消费额度 | 可用于合成状态探测，不能估计反事实质量 |
| 只有生成种子、跨平台数据不同 | 保存 324 个实际坐标实例，9 个 split 指纹匹配原 manifest | 原始数据可以被精确载入 |

现有 31 项测试在 Linux / Python 3.12.14 下全部通过。采用仅规范化 ZIP 成员路径的适配器后，原 18 条运行、144 次决策的审计 JSON 与发布记录一致；两个 CSV 的记录也一致，文件字节存在格式差异。

修正版的归档输出探测再次得到普通决策 144/144 一致、非开发完整提示 92/92 一致、父代选择 14 次不同。这是决策路径的离线证据。探测将旧候选评价赋给重新选择的父代/标签，两副本的 B 和 M 会逐步分化，所以后续不是两个完全相同的状态，也不是实际模型产生的子代。建议称为“固定候选流驱动的策略状态探测”；真正同状态因子隔离由克隆状态的 fixture 提供。

## 3. 真实模型实验能支持什么

以下仍为 **v1.2 r2**，不是 v1.2.1 新结果。

| 控制器 | 运行数 | 平均 test gap | B 后续评价 | 有效子代 | 改进父代 |
|---|---:|---:|---:|---:|---:|
| niche | 6 | 5.759% | 0 | 0 | 0 |
| 固定开发（旧轮转实现） | 6 | 5.569% | 20 | 20 | 3 |
| 关系控制器（旧普通调度及 W） | 6 | 6.379% | 10 | 10 | 3 |

总计 144 个生成候选、141 个有效候选、288 次模型调用、392,242 tokens。30 次续开发里有 6 次竞争性、非精确重现的父代改进，5 次同时改善当时的全局 validation 最优。关系臂相对固定臂平均差 +0.811 个百分点，仅 1/6 配对更好。

可以保留的结论是“局部进步确实能转成真实后续开发机会”。由于旧控制器混杂且每模型只有 3 个区块，既不能声称关系排序有效，也不能从旧负结果断言修正后的排序无效。固定开发与 niche 的 −0.191 个百分点也不足以确立稳定收益。

新版已更正种子比较器的定义。旧 `shared_seed_best_test_loss` 按 test 取最小值，语义上是 oracle。额外核查三个旧区块，恰好都是 validation 选出的 seed 1 也在 test 最好，因此本批数值相同；新 runner 仍必须先按 validation 选择种子，再读它的 test 值，不能沿用 test 选优逻辑。

## 4. 新发现与启动前优先级

### P0：在线 runner 尚未接入新控制器

`discovery.py` 在 v1.2 TSP profile 下仍实例化 `V12SearchState`，`v12/run_v12.py` 仍生成三个控制器×两模型×旧区块 0–2 的 18 项任务。新 README 已诚实标注“没有在线启动器”。直接更换目录或方法名称不能切换到 v1.2.1。

应建立独立入口，显式记录 `controller_class=V121SearchState`、源码指纹、配置和实例快照。不要改旧 runner 破坏 r2 回放。必须通过假模型的完整 planner→coder→evaluate→observe 集成测试后，才接真实端点。

恢复也不能只照搬旧 runner 的“逐节点 observe，再恢复 RNG”。新控制器还维护 `decision_history`、`success_depths`、`_pending` 和开发额度。需要选择→核对 allocation→观察的完整转移回放，并验证恢复后的下一决策、额度、深度、统计与连续执行一致。旧路径只重放 observe 会遗漏决策历史统计。

### P0：发布 ZIP 与新读取器不兼容

发布 ZIP 的成员名例如 `minimax-niche-b0\\result.json`，新 `archived_runs()` 请求 `minimax-niche-b0/result.json`。本次未经修改的公开入口会直接抛出 `KeyError`。这是归档读取接口问题，不能由“31 项测试通过”排除。

本目录的 `verify_review.py` 提供独立适配：按规范化名称唯一匹配成员，读取原始字节，仍校验原始哈希；没有改 ZIP、候选源码或冻结控制器。未来维护版应加入这项兼容和针对已发布 ZIP 的集成测试。

### P0：程序哈希取决于 Python AST 展示版本

使用已发布坐标快照、原数值规范和上述 ZIP 适配，在 Linux 完成 198 个 validation、132 个 test 程序评价：

- 全部 330 次评价没有连续数值差异；除 `program_hash` 外没有离散字段差异；控制器决策错误为 0。
- 327 个有效评价的 `program_hash` 不同，因此原严格/容差验证仅 3/330 通过，原结果 `passed=false` 保留。
- 哈希来自 `sha256(ast.dump(...))`。Python 3.13 默认省略空列表字段，3.12 的默认 dump 不同。[官方文档](https://docs.python.org/3.13/library/ast.html#ast.dump)和 [CPython 3.13.5 源码](https://github.com/python/cpython/blob/v3.13.5/Lib/ast.py)说明了这个版本差异。
- 对该受限语法按 3.13 默认格式进行独立诊断序列化后，**327/327 哈希与归档一致**。见 `evidence/hash_diagnosis.json`。这项诊断不将原失败记录改成“通过”。

这已经把上一轮未逐项解释的复现问题收敛到数据生成与哈希格式：保存坐标消除了本次实例重建的浮点差别；AST 格式导致剩余哈希不同。当前没有发现路径、质量或搜索决策不一致。推荐短期锁定原 Python 3.13.5 复现环境；新版本同时保存原始代码字节 SHA-256、明确版本的结构哈希、Python 版本。不能用放宽数值容差来处理字符串哈希差异，也不能静默删除哈希检查。

### P1：发布清单包含未发布缓存

v1.2.1 新包 11/11 校验通过。当前 r2 清单有 25 项，23 个实际文件哈希通过，另外两项为未追踪的 `analysis_code/__pycache__/*.pyc`。应从跟踪文件/明确发布清单生成校验值，不把本机缓存当成复现材料；以勘误提交修正清单并保留旧标签。

### P1：多分支机会不等于族证据机会

即使两个分支都可用，它们可能属于同一标签，或者均少于两次观察而回退共同分数。这时族项不能改变排序，关系组实际上主要按局部收益排序。

在现有每模型×控制器暴露统计上，增加：可用分支不同标签数、族分数是否有差异、完整策略相对 gain-only 是否改变父代。作为机制诊断单独报告，不能根据这些指标筛选性能样本或追加成功运行。

当前 B 的“竞争性”在入池时检查；全局最佳改善后，旧条目不重新通过质量门槛。这不违反当前准入定义，但文档应写明“准入时竞争性”，并记录选择时的质量差，避免把它理解为持续质量约束。若增加重新检查，作为新设计选择在两臂共同实施并重新冻结。

## 5. 下一步研究顺序

1. **发布/集成就绪，0 调用。** 解决上面的在线入口、恢复、ZIP、哈希与清单问题；完成假模型端到端回放；新数据在搜索前保存。
2. **16 次可行性筛查。** 两模型×两个开发控制器×新区块 3–6，每次 8 个提案；回答组合排序相对 FIFO 的端到端表现。已提供不可执行的[任务矩阵草案](screening_16_jobs.draft.json)，尚不是冻结 manifest。
3. **必要时做机制归因。** 用新批次对照 FIFO、gain-only、族证据+收益、打乱族证据+收益；不能把组合策略相对 FIFO 的收益全部归因于关系。
4. **独立检验集合用途。** 搜索输出冻结后，使用独立训练和调参数据构建低成本选择器；与初始规则集、最佳单程序及同容量集合比较。
5. **根据效应和方差规划确认阶段。** 新区块、多任务和强基线须另行冻结，不能把探索性批次拼接成确认性结论。

当前不建议增加完整关系图、W、witness 或更多 LLM 角色。先检验已有信号是否值得占用预算。详细执行步骤、字段、失败规则和统计方法见 [EXPERIMENT_PLAN.md](EXPERIMENT_PLAN.md)。

## 6. 第六章如何承接前文

第三章提供质量与分布分别评价的依据；第四章提供多解维护、局部开发及按过程证据分配资源的机制来源；第五章提供区分质量空间与行为/决策空间的建模视角。第六章需要证明这些机制迁移到程序搜索后有实际价值，而不能仅用 Planner/Coder/Memory 的模块名称作为创新。

还应明确：第四章同一 TSP 实例上的不同高质量路线，与第六章跨实例执行的不同程序行为，不是同一个模式定义。有限 probe 行为簇不是已知真实算法模式，单目标原型也不等于已经验证高维多目标优化迁移。

建议章节按“程序搜索对象与证据定义→A/B/M 分支开发→有限族证据排序→严格对照→搜索与集合用途→失效边界”组织。如果只有固定开发有效，保留该结论，收缩关系创新主张；若集合选择器无增量，明确成果是单程序发现/分支开发，不能声称已证明多模态集合的部署价值。
