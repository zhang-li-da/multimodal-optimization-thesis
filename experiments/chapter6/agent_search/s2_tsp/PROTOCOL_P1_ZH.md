# S2-P1 TSP 保护机制因子实验协议

本协议在任何新的搜索模型请求前固定。它只使用本机 OpenCode 的
`minimax-cn-coding-plan / MiniMax-M3`，不声称跨模型泛化。

## 研究问题

在普通搜索和提示接口完全相同的条件下，把“质量合格且相对父代有实质改进”的候选放入有限开发池后，是否需要一个能够兑现开发额度的保护调度，才能使局部改进转化为后续搜索和最终 TSP 质量？

## 因子与预算

| 因子 | 水平 |
|---|---|
| 开发池保护 | `fb_unprotected`、`fb_protected` |
| 模型 | MiniMax M3 |
| 新数据块 | 14--19 |
| 搜索种子 | 0、1 |
| 每次搜索 | 8 个提案，最多 16 个模型请求 |
| 输出上限 | planner 1800，coder 2000 |
| 每次搜索 token 预算 | 120,000（超出即停止并保留缺失） |
| 每次搜索墙钟预算 | 1,800 秒 |

两组共享同一块数据、搜索种子、三个手写初始规则、语言约束、planner/coder 接口和总提案数。组名不会写入模型提示。新方向的累计额度不会因重新入池、改名或候选替换而重置。

## 机制定义

候选只有同时满足以下条件才进入开发池：程序有效；验证损失处于初始最好规则加 3.5% 的共同质量容差内；相对实际父代改善超过 `1e-4`；不是已观察行为和逐实例损失的重现；结构方向不是 `unknown`。

`fb_protected` 为每个新方向提供最多 2 次启动机会，容量为 4；启动机会在后续提案中优先兑现，且每次实际开发都会扣减。满容量时不能驱逐尚有未兑现启动机会的方向。成功的非重复分支可以在累计 8 次方向尝试内获得有限续额，但总额度不重置。

`fb_unprotected` 使用同样的入池和审计记录，但不安排开发池专用时隙；它只执行固定 50% 的探索/开发动作，开发动作没有可保护的方向父代。这是保护机制的关闭对照，不把“进入池”计作“得到开发”。

两组的普通探索都使用相同的固定标签轮转。开发选择采用 FIFO 规则，避免在本阶段混入族频率或收益排序的额外因素。这样可以把主要差异归因到“额度是否被兑现”。

## 主要结果

对每个 block-seed 配对报告：验证选择的程序在 test 上的 gap、相对未保护组的配对差值、有效候选数、入池数、保护时隙计划数与实际兑现数、多个分支可选次数、分支父代改进次数、最终最好程序的祖先是否来自受保护分支、tokens、请求数和墙钟时间。bootstrap 单位是 block-seed 配对，不能把实例或 API 请求当作独立重复。

这是一轮因果机制筛查，不预设保护组必须获胜。若保护改变了决策但没有质量增量，报告为机制有效而质量无增量；若保护本身没有兑现，下一阶段先修复执行链；若保护稳定劣于关闭组，收缩第六章主张。
